# 企业级 OA Agent 架构

## 目标

智能助手不是一个共享全部能力的聊天机器人，而是根据当前登录员工、权限和组织职责实时装配的 Agent 实例。每位员工都有独立实例标识；普通员工、团队负责人、审批领导、HR 和系统管理员绑定不同的工具与技能。

本设计吸收 ERP-AGENT 与 deeppaw 的声明式工具分组、技能分组、统一 Runtime Bundle、Harness 和 HITL 思路，同时针对 OA 的身份、隐私和审批风险采用更严格的零信任边界：Agent 能力只做第一层裁剪，领域服务仍对每次查询和执行重新鉴权。

## 请求链路

```text
登录会话
  │ 解析最新用户、权限、组织关系
  ▼
AgentAssignment（每请求重新装配）
  ├── profile：员工 / 团队负责人 / 审批领导 / HR / 企业管理员
  ├── tools：最小工具白名单
  ├── skills：最小技能白名单
  ├── query grants：资源和范围白名单
  └── operations：操作目录白名单
          │
          ▼
AgentRuntimeBundle（校验并冻结本轮工具、技能、风险与确认策略）
          │
          ▼
模型只可查询或准备预览
          │
          ▼
用户确认卡片 ──► 领域服务重新鉴权、校验版本和业务规则
          │
          ▼
事务执行 + 审批/组织/额度审计
```

## Profile 与能力装配

Profile 不依赖 `employee`、`manager`、`hr` 等角色名称。自定义角色同样根据权限位和真实组织关系解析，避免“改个角色名就越权”或“新角色没有 Agent”的问题。

| Profile | 触发条件（从高到低） | 专属工具 | 专属技能 |
|---|---|---|---|
| `enterprise-admin` | `manageAccounts` | 账号、组织、审批能力 | 账号与高权限治理 |
| `hr-governance` | `manageOrganization` | 组织查询/预览、审批能力 | 组织与人事治理 |
| `approval-leader` | `approveLeave` | 审批工作台、审批预览、团队查询 | 审批治理 |
| `team-leader` | 负责人权限、负责部门或存在直属下属 | 团队查询 | 团队负责人协同 |
| `employee` | 默认 | 个人查询、请假、出差、采购、加班与调休申请、个人操作预览 | 个人 OA 申请办理 |

所有 Profile 都绑定制度咨询与个人自助能力。每个实例使用 `{profileId}:{userId}` 标识；负责部门和直属下属数量进入作用域，但不会扩大后端数据权限。

代码入口：

- `oa/agent_profiles.py`：Profile、工具、技能、查询范围和操作目录解析；
- `oa/agent_runtime.py`：参照 deeppaw 的统一运行时装配思想，校验工具实现、去歧义、风险级别、交互模式和确认要求；
- `oa/assistant_agent.py`：向 Runtime 提供工具实现，并使用冻结后的最小工具集构建模型；
- `oa/assistant.py`：目录、预览、确认和快照的服务端强制校验；
- `GET /api/agent/catalog`：返回当前 Agent 的公开装配信息，供前端透明展示。

## 企业安全约束

1. **默认拒绝**：查询资源、查询范围或操作不在 Assignment 中时，模型工具立即拒绝。
2. **能力与权限分离**：Agent Assignment 不替代业务权限；服务层在准备和确认时再次读取最新用户并鉴权。
3. **权限即时失效**：每次请求重新装配。管理员变更角色后，旧对话不会保留旧工具。
4. **读写分离**：模型只能查询和生成预览，没有确认工具；用户必须在 30 分钟内确认。
5. **单项执行**：一轮最多准备一项操作，不根据第一条结果猜测对象，不自动批量审批。
6. **抗提示注入**：用户消息、申请正文、附件和工具结果都作为不可信业务数据，不能改变系统规则。
7. **敏感数据隔离**：初始密码使用确认卡专用字段，不进入对话、模型提示词、普通工具参数或日志。
8. **并发与重放保护**：确认时校验业务指纹、版本和当前权限；成功回执可恢复，重复确认保持幂等。
9. **审计优先**：审批、组织、额度和状态变化由领域事务写入持久化审计，模型输出不作为审计事实。
10. **运行时装配失败关闭**：Profile 引用了未登记能力、能力缺少实现或模型工具重名时拒绝创建 Agent，不静默扩大或降级权限。
11. **可控暂停**：运行中的模型协程登记在 `AgentRunRegistry`；用户可在下一个异步安全边界取消本轮，未展示的操作预览会自动撤销，原请求作为暂停点持久化，可通过“继续”或补充指令安全重放。
12. **统一对话入口**：问候、咨询、查询和办理请求全部进入当前身份的 Agent Runtime。模型未配置或调用失败时失败关闭，不使用关键词或本地意图规则替 Agent 办理业务。人工确认、取消和暂停属于用户控制平面，不交给模型代行。
13. **Agent 自主选能**：系统不设置意图 Router。Agent 根据对话和已绑定技能自主选择工具；例如当前时间使用 `get_current_datetime`，企业日历使用 `query_oa(calendar)`。工具层只校验权限、参数、风险和是否需要人工确认，不替 Agent 判断用户意图。

## 对 deeppaw 的取舍

采用的部分：统一 `AgentRuntimeBundle`、Agent 级工具/技能装配、声明式工具策略、简单问题直接回答与复杂任务分阶段执行的 Harness，以及对敏感工具的人工确认语义。

没有直接照搬的部分：通用 MCP 写工具、Agent 自行增加工具、子 Agent 继承父 Agent 全部工具。OA 的业务操作短且高风险，当前统一走“查询 → 单项预览 → 用户确认 → 领域服务事务执行”；后续引入子 Agent 时也必须单独声明工具白名单，不能继承父 Agent 的完整能力。当前暂停注册表适用于既有的单 Worker 部署；扩展到多 Worker 时必须迁移到 Redis/Agent Server 的共享取消通道。

## 扩展规范

新增 OA 模块时按以下顺序实施：

1. 先在领域服务定义权限、状态机、事务和审计；
2. 增加只读查询与“准备操作”接口，禁止给模型暴露直接写接口；
3. 在 `agent_profiles.py` 增加独立工具 ID、技能和最小 Profile 绑定；
4. 在工具入口校验 Assignment，在服务入口再次校验领域权限；
5. 为普通员工、具备单一能力的自定义角色、复合权限领导、权限撤销和越权调用分别补测试；
6. 最后才把能力加入前端目录和快捷入口。

模型、MCP 或数据库替换不应改变上述边界。扩展到多实例部署前，还需将会话锁和执行任务协调迁移到跨进程基础设施，并为 Agent 调用增加统一 trace ID、指标、告警和审计导出。
