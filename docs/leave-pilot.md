# 请假部门试点

本轮面向一个部门使用年假、事假和病假的场景。员工准备申请，系统计算时长并提示问题，指定审批人作最终决定，HR 维护人员、工作日历和额度。没有选择实际试点部门，也没有修改公司真实员工、日历或余额；这些由 HR 在启用前配置。

## 入口与使用

| 使用者 | 页面 | 可完成的工作 |
| --- | --- | --- |
| 员工 | 发起请假、我的申请 | 保存草稿、编辑、上传材料、提交、撤回、重提、催办、申请部分或全部销假 |
| 审批人 | 我的审批 | 查看建议和材料、批准、驳回、退回补充、交接请假或销假待办、查询处理记录 |
| 员工 / HR | 假期台账 | 员工查本人；HR 选员工查看、调整额度并写明依据、导出 CSV |
| 全员 / HR | 工作日历 | 全员查看；HR 设置节假日和补班，也可恢复默认工作周 |
| 全员 | 消息通知 | 待办、审批结果、退回、销假、交接、额度调整；已读管理与关联申请 |
| HR | 请假管理 | 查看最近 500 条未隐藏申请，按部门和状态筛选，打开详情转交积压审批 |

AI 可辅助从自然语言准备请假、审批和管理操作，查询制度与待办，生成摘要及风险提示。**所有请假和销假都需要人工审批**，短时申请也不自动通过。智能助手中的操作卡片支持人工确认批准、驳回和交接；模型没有执行确认工具。未配置模型或模型不可用时对话能力失败关闭，可使用聊天内“办理业务”表单。材料由人工核验，AI 当前不读取附件内容。具体范围见 [对话办事说明](conversation-workspace.md)。

## HR 启用顺序

1. 按 README 初始化系统管理员并分配 HR 账号，再录入试点部门真实员工和审批人。示例员工不代表公司真实账号，不能直接用于正式试点。
2. 检查每位员工的所属部门、直属领导、单独指定的请假审批人和账号状态。审批人必须是启用且有审批权限的其他员工。没有有效审批人时不能提交。
3. 在工作日历中逐日设置试点覆盖期间的法定节假日、公司假日和调休补班。默认周一至周五 09:00–12:00、13:30–18:00，共 7.5 小时；周末休息。当前不支持轮班、按员工不同工时或半天日历例外。
4. 按公司制度核定初始可用额度。新员工入职填写总额度；旧员工通过台账调整总额度并写明依据。当前不自动计算工龄年假、跨年清零、结转或按月累积。HR 调整不能低于已用额度，单假别总额上限 2000 小时。
5. 核对系统试点规则是否适用：假别、工作时段、提交限制、材料和审批人。内置“系统试点规则”是系统行为说明，不应当作已由公司正式颁布的制度。不同制度需要先调整规则再使用。
6. 在测试环境用员工、审批人、HR 三个账号执行下表验收，确认权限和额度符合公司预期后，再让选定部门启用。试点期间每天查看超时待办与异常反馈。

当前只能提交尚未开始的请假，不提供事后补请。手工录入的时间和工作日历统一按北京时间计算。上传证明材料、工作交接的必填要求由审批人按公司制度核验，未做按假别自动强制材料清单。

## 流程及账务规则

草稿或退回、驳回、撤回后的申请可以编辑。保存后成为草稿，员工再次确认提交，历史处理轮次与字段修改记录保留。审批中先撤回再修改；已批准申请通过销假处理，不能直接修改。页面操作携带版本，旧页面上的修改、批准、转交和提交会提示刷新。

请假时长由工作日历计算。草稿保存时记录工作时段；提交时如日历已变化，要求重新编辑保存并确认。提交后日历调整不会改动该单据时长，销假仍使用原单据工作时段。批准时再次校验余额和与其他有效申请的冲突；待审批时不占用余额。同一员工有重叠申请时须先撤回或退回其中一条。

批准与扣减、销假批准与返还均在同一数据库事务中执行。销假可以分段申请，已批准或待审批销假时段不能重叠。待审批销假不释放额度或时间；批准后释放对应工作时段，全部工作时段销完才显示“已销假”。时长单位为小时，保留两位小数，分次销假按累计剩余时长结算，避免拆分造成舍入误差。HR 调整通过操作编号避免网络重试重复入账。

首次升级为已有余额创建一次“期初”流水，不伪造历史扣减明细。**没有可核对扣减流水的旧版已批准单据不能自动销假返还**。HR 应核对旧系统记录、实际休假和当前余额，通过带原因的额度调整完成对账；历史单据保持原状态，调整在台账留痕。试点应以升级后的新申请为主。

审批交接立即改变当前处理人，旧处理人不能继续批准，历史记录保留。HR 可协助转交，请假和销假待办均支持。交接当前单据不改变员工今后的默认审批人；后者在组织与人员中维护。停用或移除审批权限前须清空该账号的待审批任务。

## 材料与通知

- 材料限 PDF、PNG、JPG，每份不超过 5 MB，每单不超过 10 份。上传和下载校验申请访问权限，下载使用附件响应。检查文件后缀、文件签名和部分 PDF 主动内容；这些检查不等于病毒扫描。
- 从未提交过的草稿可移除传错材料；提交过的材料保留，不再删除。更正时上传补充材料并说明，必要时新建申请。文件存于 SQLite，备份数据库会包含材料。
- 通知与业务变更写入同一数据库。页面约每 30 秒刷新，后台每 60 秒检查超过 24 小时的待办，每个待办每天提醒一次；员工手动催办每个 UTC 整点小时最多一次。
- 通知为站内消息，不发送短信、邮件、企业微信或钉钉。员工需要登录查看，HR 仍需在试点期间跟进待办；不应把站内消息当作已送达员工手机。
- API 启动时将中断的 AI 审核转回人工；原审批人不可用则通知员工联系 HR 后重新提交。模型出错或超时不会自动批准。

## 试点验收

| 场景 | 通过条件 |
| --- | --- |
| 员工保存、上传、提交，主管批准 | 申请与材料可见；批准前不扣减，批准后只扣一次 |
| 主管退回补充、员工修改重提 | 两轮处理和修改前后记录保留；旧版本提交或批准被拒绝 |
| 驳回、撤回再编辑 | 原单据恢复草稿，可再次提交，无重复余额扣减 |
| 节假日和周末补班 | 新申请时长符合日历，旧申请和销假按原快照结算 |
| 部分、全额销假 | 人工批准后返还，重复点击和重复时段不会重复返还 |
| 余额不足、时间冲突 | 无法批准，申请和余额保持一致，可退回处理 |
| 请假、销假交接 | 新审批人收到待办，旧审批人不可处理，可查看历史 |
| 越权访问 | 其他员工不能查看申请、材料和台账，不能标记他人通知 |
| HR 额度调整 | 原因和操作人可查询，重复请求只记一次，CSV 可导出 |
| 模型失败、进程重启 | 申请能转人工继续，不丢失账务或重复批准 |
| 手机浏览器 | 主要页面、申请详情、日历、台账在 390 / 320 像素可操作 |

自动化验证入口为 `npm run check`、`npm test`、`npm run build`。新业务测试位于 `apps/api/tests/test_pilot.py`，使用临时数据库，覆盖上述核心异常和账务场景。真实员工及公司制度验收仍需在试点前完成。

## 运行边界

使用 HTTPS、正确的 `WEB_ORIGIN` 和 `AUTH_COOKIE_SECURE=true`，前后端推荐同源代理。当前使用 SQLite 和单 API 工作进程，服务需要持续运行。上线前使用 SQLite 在线备份接口备份，并在独立路径恢复验证员工、台账与附件；运行中不要仅复制主数据库而忽略 WAL。

第一阶段未覆盖多级/会签流程、委托时间段、考勤薪资对接、企业通讯录同步、SSO、异地灾备、附件病毒扫描和多服务部署。已处理页面按申请展示最近一次本人动作，完整的历次请假与销假动作在详情中。消息页面显示最近 200 条；请假管理显示最近 500 条，扩大范围前需要补分页和更细的数据权限。
